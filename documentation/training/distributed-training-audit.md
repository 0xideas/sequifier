# Distributed training audit and implementation plan

**Historical baseline** `d18473ef24cb603361a4df762d94e27e91d71649`, 2 June 2026. **Current revision** `12bd5559e487570bf998b732b64f382ed41a74ae`, branch `ft/equalise`, 23 November 2026. The reported production result is ten nodes with four H100s each. The report of that run establishes that a configuration at the baseline trained across 40 GPUs. The exact launcher script, strategy, precision, shard distribution, worker count, checkpoint exercise and throughput for that run are unspecified. The code account below covers both available strategies and identifies their respective constraints. [Historical tree][old-tree] · [Current tree][new-tree]

| Question | Finding |
| --- | --- |
| Does current supervised training retain the validated approach? | **Yes for the basic execution model, partially for the precautions.** It still runs one process per GPU, uses global rank to divide work, routes training through DDP or composable FSDP, aligns steps, reduces metrics and coordinates publication. Padding and loss normalization improved. DDP parameter participation, validation buffers, FSDP-compatible parameters, recovery traffic, and a lazy-loader memory check prevent a blanket claim of parity. |
| Does policy learning use the same distributed implementation? | **No.** Imitation, IQL, DPO, PPO and GRPO use a local learner with local model roles, sampler, updates, clocks, checkpoints and writers. GRPO can parallelize simulators. Mixed plans explicitly require local execution. |
| What should be implemented first? | Fix the demonstrated supervised failures and validate the existing path on the cluster. Extract launch and collective ownership above the plan, then add rank-aware policy role execution, global work assignment, durable recovery and algorithm-specific reductions. Keep existing single-process behavior as the numerical and artifact reference. |

## 1. How the baseline ran across nodes

### Launch, identity and operating conditions

1. The CLI loads the config, sets float32 matmul precision in the launching process, and tests whether the training path is a directory. With distribution disabled it calls one worker directly. With `training_spec.distributed: true`, the presence of **both** `RANK` and `WORLD_SIZE` selects external launch. The worker takes global rank and actual world size from the environment, and `LOCAL_RANK` with a default of zero. Without that pair, `mp.spawn` starts the configured number of local processes, joins them, and sets global rank equal to local rank. A child exit code of 143 is mapped back to 143 by the parent. There is no cross-node spawner in Sequifier. [Historical launcher][old-launch]
2. At 10 × 4, one torchrun agent per node with four workers gives 40 global ranks and local CUDA indices 0–3 on each node. A rank such as 37 can own GPU 1. CUDA selection and DDP device IDs use the **local** index. Shard assignment, process-group membership, logs and single-writer decisions use the **global** index. All workers require a consistent configuration, data manifest, model/checkpoint namespace and a reachable rendezvous. Slurm task identifiers alone do not set up this program. Its guide assumes shared project/data storage and NCCL for NVIDIA GPUs. [Historical worker][old-worker] · [Historical deployment guide][old-guide] · [torchrun environment][torchrun]
3. The worker sets the CUDA device before group initialization, configures rank-specific logging and initializes the group before creating the datasets. It preserves externally supplied `MASTER_ADDR` and `MASTER_PORT`, defaulting to `localhost:12355`. That default serves a local job. Across nodes each agent needs the same reachable master address and port. The helper supplies explicit rank, world size, backend, and a CUDA device ID when CUDA is available. It uses `NCCL_TIMEOUT` as an application-specified process-group timeout in **seconds**, default 1,800. The code sets `NCCL_DEBUG=INFO`, `TORCH_DISTRIBUTED_DEBUG=DETAIL` and, in the training module, `TORCH_NCCL_ASYNC_ERROR_HANDLING=1`. The point at which Torch reads a particular setting matters. Set diagnostics in the launching environment when relying on them. [Historical environment][old-env] · [Historical training module][old-module]
4. DDP replicates the whole network and optimizer on each rank and synchronizes gradients. FSDP2 shards parameters, gradients and optimizer state over one world-wide group, gathers parameters for computation and reduce-scatters gradients. Both perform data parallel training. Neither scheme partitions examples into pipeline stages or configures node-specific tensor parallelism. Each node needs enough host RAM for its loaders and checkpoint work. Both branches construct and place the full initial model before distribution, so initialization itself has a per-device memory requirement. [Historical wrapping code][old-wrap] · [PyTorch FSDP2][fsdp]

### Data placement was part of the synchronization protocol

The historical defaults were local execution, world size 1, NCCL when distributed, eager loading, zero loader workers, exact sampling, enabled layer autocast and outer compilation. Distributed configs had to select DDP or FSDP. FSDP required an explicit CPU-offload boolean and a compatible compile mode. DDP prohibited the offload field. Over/undersampling required a **configured** world size greater than one because validation happened before the torchrun environment replaced the spawn count. [Historical defaults][old-defaults] · [Historical validator][old-config]

Distributed training required prepared **folders** on the training path, with the corresponding folder-form validation data. The config allowed PT or Parquet and warned for Parquet. The guide prescribed `merge_output: false`, preferred `write_format: pt`, and qualified Parquet as beta because Polars threads, loader processes and shared storage could cause CPU contention, memory pressure and NCCL timeouts. The worker rejected single-file distributed training. The worker built both historical folder iterators with their default shuffling enabled and set the epoch on each. Both splits had to sustain the same collective schedule across ranks. A fast training loader could not compensate for an uneven validation loader. [Historical configuration][old-config] · [Dataset construction][old-worker] · [Deployment guide][old-guide]

| Historical mode | What each rank owned | How it equalized work |
| --- | --- | --- |
| Eager PT or Parquet | Each training process read the entire split into CPU tensors. Tensor storage was shared with its loader workers. A common permutation from `seed + epoch` was generated before taking sample indices `rank::world_size`. Each loader worker then took `worker_id::num_workers` from that slice. | `oversampling` repeated the local indices to the largest rank count. `undersampling` truncated to the smallest. `exact` returned the **local** count, without asserting equality. A one-example difference can create another backward or validation batch. An empty eager slice can make the oversampling extension loop fail to progress if the target is positive. [Eager PT][old-eager] · [Eager Parquet][old-eager-pq] |
| Lazy PT or Parquet | Each rank normally read whole files at manifest positions `rank, rank + W, …`. Each process independently computed all ranks’ sample totals from metadata. File order was shuffled within the assignment. Rows within a file used a deterministic seed including epoch, file ID and rank. Workers owned contiguous ranges of the resulting rank stream. | `exact` required **equal assigned sample sums**. Equal file counts or approximately equal sizes were insufficient. `oversampling` cycled files up to the maximum count. An empty rank borrowed a file by modulo. `undersampling` stopped at the minimum. A rank with no files raised outside oversampling, and a zero minimum made an undersampled run unusable. Cycling also required a nonempty manifest and at least one positive-size file in a repeatedly used assignment. Both modes assumed meaningful, accurate manifest counts. [Lazy PT][old-lazy] · [Lazy Parquet][old-lazy-pq] |

For a common per-rank quota `Q`, `K` effective loader workers and per-process batch size `B`, worker `i` gets `Q // K + int(i < Q % K)` examples. The advertised number of batches is the **sum of the ceilings** of those worker quotas divided by `B`. Lazy workers skip non-overlapping shards, buffer across file boundaries, and emit the last partial batch of their own range. The DataLoader uses `batch_size=None` and `sampler=None`. Its iterable supplies complete batches. It pins for accelerator transfers other than MPS, prefetches four items per worker, and persists workers when the worker count is positive. The older source comment mentioning a DistributedSampler is misleading. [Lazy worker calculation][old-lazy] · [Loader setup][old-worker]

This kept normal synchronized runs in lockstep without a DDP join protocol. Historical repeated samples counted in the loss, and undersampled examples were absent that epoch. There were two worker-process caveats. The iterators queried the process group inside the worker, falling back to rank 0/world 1 in a freshly spawned loader process. And `set_epoch` wrote a plain Python attribute in the parent, which persistent worker copies could miss. At 40 ranks, a validation split with only 39 real windows is an instructive boundary case. Historical eager exact gives the last rank zero batches. Its peers can enter forward/reduction while it advances to a later collective. The current masked fallback keeps all 40 participants in the same schedule. [Historical eager iterator][old-eager] · [Historical lazy iterator][old-lazy] · [Historical epoch loop][old-epoch]

### Model setup, updates and decisions

- **Reproducibility and compilation.** Each training worker seeded Python, NumPy and Torch, including CUDA, before model construction. The workers used the same initialization seed. cuDNN deterministic mode was enabled and benchmarking disabled. The optional deterministic-algorithms mode was warning-only and set a cuBLAS workspace option. The model registered its causal mask as a nonpersistent buffer. The CUDA-only worker branches supported DDP with `none` or `outer` compilation, FSDP with `none` or `inner`, and local training with either. The validator rejected the incompatible DDP/FSDP combinations. The training module enabled Dynamo error suppression. [Historical seed setup][old-seed] · [Model device and mask][old-model] · [Config checks][old-config]
- **DDP.** Build the full model on the local device, initialize its optimizer for a fresh run, optionally compile the outer network, then wrap with `DDP(device_ids=[local_rank], find_unused_parameters=False)` on CUDA, or no device IDs on CPU. The uniform historical network and loss were expected to exercise the trainable parameters on each rank. On CUDA every rank ran a no-gradient dummy forward through the wrapper, using configured batch size and sequence length and type-appropriate ones. Warm-up used BF16 autocast if requested, followed by a group barrier. Training **and validation** called the wrapped module. [Historical DDP branch][old-ddp] · [Historical evaluation][old-eval]
- **FSDP.** Construct `init_device_mesh("cuda", (world_size,))` explicitly. Call `fully_shard` on each encoder layer, then on the root, using the same mesh. This groups layer collectives and leaves the residual parameters in the root group. Use the public FSDP import from Torch 2.6 onward and the earlier composable import below that. With layer autocast enabled, use the configured linear dtype, default BF16, for parameters in computation, gradient reduction and output. Use the FSDP policy for those casts. Barrier after sharding, construct the optimizer from the resulting parameters, restore if applicable, optionally compile inner layers, execute a no-gradient dummy CUDA forward, and barrier again. The training callable is the in-place sharded network. The flag named `fsdp_cpu_offload` selected the base `OffloadPolicy()` when true. PyTorch defines that policy as no offload. The old flag is weak evidence of actual CPU offload on the cluster. [Historical FSDP branch][old-wrap] · [PyTorch policy definitions][fsdp]
- **Backward and update.** Each rank transferred its own batch, ran the distributed callable, computed locally masked per-target means and applied target weights. The first categorical target supplied the nonzero-position mask, or, for real-only targets, the mask began at the first nonzero value in each sequence. That common mask covered every target. Non-FSDP training used device autocast when enabled, normally BF16 absent a linear override. The scaler was enabled by an explicit FP16 layer dtype. Every microbatch ran synchronized backward. Accumulation delayed the optimizer step until the configured boundary or final batch. It summed microbatch gradients without division by the accumulation factor. At a step it unscaled, clipped the norm to 0.5, stepped, updated the scaler and zeroed gradients. A batch scheduler could advance on every microbatch, including one without an optimizer step. Full batches correspond to `W × B` sample slots per backward and `W × B × A` per full accumulation window. At 40 ranks, with batch size 16 and accumulation 4, those are 640 and 2,560 slots. Partial worker tails, repeats, and valid-token counts change the actual weight of data. The software did not automatically scale the learning rate. [Historical training step][old-step] · [Historical objective][old-loss]
- **Validation, logging and stopping.** All ranks participated in optional initial, epoch-end and requested mid-epoch validation. Evaluation computed means of batch losses on each rank and SUM-reduced the total and sorted per-target means, dividing by world size. It also computed/reduced a one-time persistence baseline. This gives a mean of rank means, which can differ from a global valid-token mean. Training console loss and last-batch class-share information were rank-zero observations. Best selection, early-stopping counters, NaN handling and epoch scheduler progress followed the common validation result. Console and common outputs were owned by rank zero, with separate diagnostic logs for each global rank. [Historical evaluation][old-eval] · [Epoch decisions][old-epoch] · [Historical logging][old-seed]
- **Time and operator control.** Rank zero checked the clocks for rolling latest and retained batch saves. It broadcast both flags, synchronized ranks, optionally had everyone evaluate, and broadcast the validation scalar before every rank entered the requested capture. The code did that communication even on ordinary batches. Epoch saves followed a deterministic cadence. For Optuna the primary checked the prune file, broadcast the decision, and all ranks cleaned up and exited 143. On KeyboardInterrupt the handler attempted a barrier, a rank-zero prompt, a broadcast answer and collective state capture. This assumes all workers can reach the handler. The subsequent common finalization also gathered/exported last/best even after declining the interactive export. It was never a fault-tolerant protocol for a dead worker. [Historical save flags][old-flags] · [Prune and interrupt handling][old-epoch]

### Checkpoint and export constraints

All ranks had to enter FSDP state extraction. The full model and optimizer were gathered with `full_state_dict=True, cpu_offload=True`. Rank zero retained/wrote full CPU state, removed compile-name prefixes and selected best/last for export. The normal finish bracketed full-state extraction and rank-zero export with barriers. DDP could use the underlying replica’s state, and the old best-state helper cloned it on each rank. Rank zero rebuilt a separate unwrapped export model for enabled predictive or embedding PT/ONNX products. Its constructor inherited the configured device despite a comment describing a CPU model. Single-writer publication still required sufficient memory on that rank. [Historical state extraction][old-capture] · [Historical save][old-save] · [Historical export][old-export]

Each process looked for the newest model-name-prefixed checkpoint by filesystem creation/change time. In the FSDP resume branch, rank zero opened the selected file on CPU, derived next epoch/batch, and broadcast a Python object list containing the full model, optimizer and scheduler. All ranks then used distributed state-dict setters. That limited parallel full-file reads but still replicated a large serialized payload across the world. The DDP resume branch loaded the file on every rank and tried to load optimizer/scheduler **before** its explicit optimizer construction. This is a defect in the historical branch. Historical checkpoints stored epoch, batch, weights, optimizer, scheduler and loss. They omitted rank RNG, scaler, best/patience state, loader state and pending accumulated gradients. A mid-accumulation timed save could therefore skip contributions on resume. The writer used direct `torch.save`. On resume the worker compared the next batch to its reconstructed loader length, advanced the epoch at the boundary, and otherwise iterated past the saved batches. A changed world size, shard order, sampling mode, worker count or batch size could therefore change what the recorded cursor meant. The reported scale-out and the source-level limitations on exact replay can both hold. [Historical restore paths][old-wrap] · [Historical save payload][old-save] · [Checkpoint selection][old-latest]

### Current gaps with operational consequences

1. **A valid single-interface model can break DDP reduction.** Dataset/interface count is an insufficient proxy for gradient participation. A real predictor can own a learned Gaussian scale while a phase optimizes MSE. The scale is returned by forward but MSE does not consume it. A two-rank run failed on both replicas with an unfinished reduction. Zero-weight heads, optional heads and changing phase masks need the same reachability audit. Forcing a zero gradient onto an unused parameter can change weight decay or optimizer state, so it is important to preserve the distinction between an unused gradient and a numerical zero. [DDP choice][build] · [Forward outputs][network] · [Loss routing][loss]
2. **The sharded parameter contract excludes a current feature.** Both construction and attachment create learned log scales as zero-dimensional parameters. Torch 2.14 FSDP2 rejects such managed parameters when checking them for sharding. This affects GaussianNLL training and policy actions that use a learned model scale. Also inspect out-of-forward parameter reads, such as decoder L2 and prediction-scale fallback, before changing which modules reshard after forward. [Model scales][scales] · [FSDP2 check][torch-scalar] · [Decoder regularization][decoder]
3. **DDP validation can evaluate different model buffers on different ranks.** The historical evaluator called the wrapped network. The current engine passes `run.network` to evaluation, bypassing the DDP callable and its buffer broadcasts. A final training forward can update each replica’s BatchNorm running statistics from different local data. All-reducing losses then combines measurements of different predictors. FSDP is in-place and does not have this particular wrapper bypass. Restoring RNG around warm-up also does not undo an update to running statistics. [Evaluation entry point][engine] · [Evaluation forward][evaluation] · [DDP buffer semantics][ddp]
4. **The lazy PT path can reject data well inside the configured RAM limit.** The measured decoded chunk is compared with a per-shard estimate computed from payload and row sizes. The estimate can miss fixed Python/tensor overhead. Increasing the run budget alone does not increase that chunk estimate. This reproduced during validation on both ranks. It is a loader defect that also matters to single-process training. [Estimate and assigned limit][ram] · [Runtime check][windows]
5. **Recovery and best-model transfer can become bottlenecks before training does.** Each worker selects and deserializes the complete current supervised checkpoint, including full model/optimizer state. A best-to-next-phase handoff uses `all_gather_object(selection.weights)[0]` for full CPU weights. After a resume, non-primary ranks can also hold the restored best weights. Object all-gather serializes and pads payloads to the largest rank. Even when only one rank supplies weights, aggregate allocations can grow with world size on **each** rank. DDP also clones full CPU weights on every rank during capture. At optimizer-safe boundaries `RunState.snapshot()` deep-copies selection, potentially copying a complete best model repeatedly, and integration state is gathered even when empty. These paths preserve useful semantics at small scale but spend memory, storage bandwidth and collective time at 40 ranks. [Restore and identity][build] · [Best handoff and boundary capture][engine] · [Snapshot][state] · [Strategy][strategy] · [PyTorch object collectives][objects]
6. **Readiness, failures and interrupt behavior differ.** The sharding barrier remains. There is no dedicated warm-up-complete or final post-export barrier. On a normal standalone finish peers can leave after collective capture while the primary is exporting. A worker-side error can send peers into their next collective until the launcher aborts or times out. In particular, the exception path can still call `flush()`, which itself may enter collectives, even though it avoids a distributed emergency checkpoint. Rank-zero-only file/lock/preflight failures need coherent propagation. The cooperative interrupt prompt in the baseline is unsuitable for a lost rank. Preserve the existing durable last-committed recovery contract. [Worker teardown][launch] · [Engine completion and exceptions][engine] · [Exporter][exporter]

The historical guide’s batch-size calculation still applies to full, equal-length supervised windows. Consider two ranks contributing 100 and 10 valid tokens with local mean losses 1 and 3. Equal rank weighting gives 2. The current token-weighted result is `(100 × 1 + 10 × 3) / 110 ≈ 1.182`. For this reason, exact reproduction of the historical loss curve is a poor acceptance criterion when masks, padding or accumulation differ. Compare the current distributed calculation to a current single-process calculation over identical logical examples. ## 3. Where the policy path diverges

### Entry points, ownership and state

The training dispatcher chooses a native supervised run, a native policy run for compatible policy phases on one interface, or a coordinator for successive groups. Distribution is a property of `run.execution.supervised`. Policy execution exposes compilation, and offline execution exposes an episode cache. The validator rejects supervised execution settings in a policy-only plan and distributed supervised settings in a mixed plan. It also checks manual layer pre-casting and the portable predictive export contract for policy plans. Even the supervised subgroup of a mixed run constructs an execution environment with rank 0, local rank 0 and world size 1. The dedicated policy API reaches the same local plan. The coordinator also rejects the supervised integration API and its semantic grouping override on plans containing policy phases. Policy roles still have their own authored optimizer groups. [Execution settings][settings] · [Capabilities][caps] · [Dispatch][coordinator] · [Group adapters][groups] · [Policy API][learner]

Starting the current policy command under torchrun starts independent invocations. With common paths and functioning shared filesystem locks, the invocations contend for an exclusive lock on the checkpoint directory. A later invocation can find a completed run or start again according to the recovery settings. With separate paths they can train separate models. None of those routes gives one actor a synchronized gradient. The policy runtime also uses the configured device and rank-zero logging/writers directly. A launcher giving each process visibility of four cards does not by itself bind these learners to four distinct cards. [Plan lock][coordinator] · [Lock implementation][lock] · [Learner and publication][learner] · [Metric writer][rl-metrics]

The coordinator handles incoming models, history-only transfer, selected phase handoffs, dependency and reference identities, committed phase artifacts and recovery envelopes. The policy learner has semantic parameter selection, independent role optimizers and schedulers, finite-gradient checks, per-role clipping, a transaction boundary, model selection, stopping, event telemetry, and exact or reset-environment continuation. Today each operates over local models, one sampler and local clocks. Checkpoint capture clones ordinary module state and saves ordinary optimizer state. Its RNG helper can capture **all visible CUDA devices**. Copying that verbatim into each GPU process could initialize contexts or look up RNG state on its siblings. [Coordinator][coordinator] · [Phase session][session] · [Role optimization][roles] · [Policy checkpoint][rl-checkpoint] · [RNG capture][rng]

The most consequential interface difference is the **forward call**. Action scoring constructs a joint distribution, calls the underlying encoder, and may call decoders repeatedly as an action prefix grows. Critics use custom calls for prepared representations. IQL indexes individual Q modules in a role container. Policy compilation patches selected methods for the life of a phase. Wrapping only the network object at construction would leave training paths that enter below a DDP or FSDP root. A distribution object whose evaluation invokes trainable modules after a wrapped forward returns has the same problem. Each scoring, value and Q operation needs an explicit managed forward whose tensor results are the ones differentiated. [Joint scoring][joint] · [Critics][critics] · [Policy compilation][rl-compile] · [DDP forward contract][ddp] · [FSDP forward hooks][fsdp]

### What must remain true for each algorithm

| Algorithm | Unit of work and current update | Distributed consequence |

| IQL | Each iteration draws one batch of transition indices **with replacement**. It evaluates frozen twin target Qs, fits the expectile value and twin online Qs, and updates the actor by a capped advantage-weighted log likelihood. Only bootstrappable successors are evaluated. There are actor, value and critic optimizers and two Polyak targets. Target buffers are copied after the step. | Allocate global draw positions once, retaining legitimate repeated IDs. Use one transition denominator and a fixed ordered sequence of role operations. A rank with no successors must still match peers’ sharded value-forward schedule. Take one coordinated optimizer step per role and one target update per successful transaction. Include both target networks and all clocks in recovery. [IQL update and evaluation][iql] |
| DPO | Draw preference pairs. Sum causal log probabilities over each chosen/rejected span for actor and frozen reference. Compute the scalar margin derivative without a graph, then backpropagate signed chunks. This bounds memory even when alternatives differ greatly in length. The objective weights each pair equally. | Assign whole pairs. Normalize by real pairs across ranks. Align actor/reference forward slots and differentiable chunk slots, even for an empty rank. Preserve bounded activation memory, reference identity, the margin coefficient and both signs. A token average or one independently normalized gradient per rank changes the objective. [Pair scoring and backward][dpo] · [Reference selection][reference] |
| PPO | One local adapter and persistent cursor collect the smaller of the configured horizon and remaining environment-step budget. A sealed generation carries old action log probabilities, values, rewards, boundaries and bootstraps. GAE runs along the trajectory, optionally normalizing advantages. The learner verifies old scores, shuffles decisions across optimization epochs, tests optional KL before stepping, and updates actor and value. | Define globally budgeted, independently seeded environment streams. Compute GAE on each continuous stream with its true terminal, truncated or horizon bootstrap. Combine normalization moments across the entire real rollout. Shuffle global decisions, reduce KL before each proposed group, and synchronize both optimizers and policy version. Every record must identify its stream and generation. [PPO collection and resume][ppo] · [GAE][ppo-buffer] · [PPO update][ppo-update] · [KL control][rl-batching] |
| GRPO | A group has a common reconstructible start, a fixed number of independently sampled members, a frozen reference and one actor generation. Advantages use the mean and **population** standard deviation of that group’s trajectory scores. The surrogate and sampled reference penalty are averaged within a trajectory, then across trajectories. Groups and actual environment steps have distinct counters. Optional simulator workers run CPU adapters and exchange messages with the learner, which batches actor/reference inference. | Assign globally unique complete groups, retaining start tokens, member indices and seeds. Preserve the conservative pre-collection environment cap and track actual steps once. Keep group statistics local to that group or explicitly reunite all members. Weight gradients and KL by trajectory with the existing inner length normalization. Ragged scoring and rollout rounds need a common schedule. Local simulator pools remain useful inside each GPU rank’s allocation. [Group contracts][group-collection] · [GRPO orchestration][grpo] · [Parallel collection][parallel] · [GRPO update][grpo-update] |

Online evaluation has a separate contract. It runs independent evaluation seeds and adapters, tracks completed, censored and unattempted episodes, applies a wall-time bound, and can report a missing selection value. GRPO’s score monitor requires all configured finite-horizon evaluations. Offline monitors aggregate decisions, transitions or pairs. Existing logs also report ratios, dispersion, quantiles, episode detail and resource usage. Averaging already-aggregated rank reports generally gives the wrong answer. Each statistic needs its own reduction and the primary must make one selection/stop decision. ## 5. Implementation plan

The first milestone is a trustworthy **supervised-only** release on the existing launcher. That work can reach cluster qualification independently of policy support. The later milestones introduce one distributed job per plan, followed by one policy algorithm at a time. Each milestone below has a testable exit condition.

### Milestone A — repair and qualify supervised training

1. **Fix parameter participation in the deployed forward path.** In `runtime/builder.py`, `model/network.py`, `training/loss.py` and the DDP strategy, resolve which parameters can contribute to each phase, dataset, enabled loss and intervention. Permanently freeze only parameters unused over the entire applicable plan. For dynamic routes, return precisely the differentiable outputs consumed by the objective through a training facade and use DDP’s unused-parameter handling where needed. Verify the behavior when returned auxiliary tensors are ignored, including with outer compilation. Prove a static fast path with the resolved plan before disabling unused-parameter handling. Preserve `grad is None` and grouped optimizer behavior for an intentionally unused head. Include dataset switches, a zero-weight target, a learned scale used only in a later phase, freezing/unfreezing and an entire rank with no valid tokens. [Builder][build] · [Supervised loss][loss] · [DDP contract][ddp]
2. **Make learned scales shardable.** Use a one-element parameter and retain the existing scalar semantics at the public scoring boundary, or implement an explicitly replicated and gradient-synchronized scalar. Apply the choice to both initialization and attachment. For the one-element design, migrate legacy scalar weights, optimizer moments and selectors/fingerprints that depend on parameter shape. Preserve parameter names, distribution broadcasting, predictive PT and ONNX outputs and policy log probabilities. Test fresh, attached, exact-resume and export/import under local, DDP and FSDP. Audit every gradient-bearing parameter read outside the sharded forward, including regularization and policy action scales. [Model scales][scales] · [Decoder regularization][decoder] · [FSDP2][fsdp]
3. **Synchronize evaluation and make warm-up side-effect free.** Give the evaluator a prepared callable for forward plus a canonical module for metadata, objectives and export. Use the same authoritative buffers across ranks before evaluating, snapshotting and handing off. Where an unwrapped read is essential, explicitly synchronize the buffers it uses. Preserve train/eval modes for individually frozen submodules. Snapshot/restore any mutable buffers and RNG around synthetic warm-up, or warm a disposable copy if needed. Add an all-rank readiness acknowledgment after successful warm-up. Test rank-distinct inputs with trainable and frozen image BatchNorm, resume, padded-only ranks and measured predictions of the resulting published model. A change to global batch statistics during **training** would be a separate model-behavior decision. [Evaluation][evaluation] · [Warm-up][build] · [DDP buffers][ddp]
4. **Repair the actual loader RAM bound.** Include fixed decoded-object overhead in the estimate, separate transient decode peak from measured retained bytes, and allocate a real per-worker allowance from the remaining per-rank budget after reserving other active loaders, worker copies, media caches and prefetch. Validate the estimate with observed payloads and keep a real upper bound under simultaneous reads. Report actual/allowed bytes and the part/shard in errors. Exercise tiny and large PT, Parquet and indexed data, mixed active parts, workers 0/1/many, and a deliberately insufficient real budget. [RAM accounting][ram] · [Chunk measurement][windows]
5. **Restore explicit distributed operating conditions.** Pass the resolved device into process-group setup and use an explicit world-wide one-dimensional mesh for FSDP. Choose the mesh device consistently with the supported backend. Keep the public/composable Torch import split and test the supported minimum and lock version. Use one canonical ordering for named sharding units, deduplicating tied/shared modules. Profile the root residual for nested decoders, image encoders and repeated layers before adding finer units. Make the intended DDP/FSDP precision explicit in the run report. Test FP32, BF16, supported FP16, manual dtype settings, real CPU offload, and unscaled/global gradient norms. Inject a nonfinite gradient into one shard to verify coherent skip/raise, scaler and scheduler behavior. Retain the current compile-mode restrictions and per-device support. [Strategies][strategy] · [Precision][precision] · [Optimization][optim]
6. **Bound checkpoint traffic and close publication.** Implement the store/restore protocol in milestone C for supervised first. Skip the per-update integration-state gather when no integration exists and avoid deep-copying immutable best weights at each optimizer step. Give cooperative prune/stop a consistent exit result in both launch modes. Handle recoverable primary lock, load and export errors at agreed control points. If a rank has died or a collective has failed, abort and let the launcher terminate peers without attempting another gradient flush or emergency barrier. Test failure during export and that a replay starts from the last durable boundary. [Engine][engine] · [Integration callbacks][integrations] · [Checkpoint service][checkpoints]

**Exit condition.** Reproduce the two failures in §4 as regression tests, then pass them. Verify image-buffer evaluation, unused parameters and sharded scales against a reference, run the two-phase resume case, and pass the supervised hardware ladder in §6 with DDP and FSDP. Existing supervised configs, Python integrations, artifacts, checkpoints and model selection remain usable.

A concrete Slurm template for the **current supervised** hardware gate follows. Request one scheduler task per node. Each task launches a torchrun agent that owns its node’s four visible GPUs. Set `MASTER_PORT` to an available job-specific port reachable across the allocation and set `SEQUIFIER_CONFIG` to the shared absolute config path.
```bash
#!/usr/bin/env bash
#SBATCH --nodes=10
#SBATCH --ntasks-per-node=1
#SBATCH --gpus-per-node=4
set -eu

master_host=$(scontrol show hostnames "$SLURM_JOB_NODELIST" | head -n 1)
srun --ntasks="$SLURM_NNODES" --ntasks-per-node=1 \
  torchrun --nnodes="$SLURM_NNODES" --nproc-per-node=4 \
  --rdzv-backend=c10d --rdzv-id="$SLURM_JOB_ID" \
  --rdzv-endpoint="${master_host}:${MASTER_PORT:?set a reachable job port}" \
  --max-restarts=0 --no-python sequifier train \
  --config-path "${SEQUIFIER_CONFIG:?set a shared training config path}"
```

Set `cpu_offload` explicitly for FSDP. Start each strategy with compilation `none`, then repeat with the production compilation and precision settings. Size CPU allocations and RAM for four ranks, each rank’s loader workers, simultaneous split caches and any simulator pools. Verify that every host sees the same environment, input manifests and writable output namespace. Record the rendezvous and NCCL diagnostics for the actual fabric. [Current settings][settings] · [Deployment guide][new-guide]

**Release decision.** Qualify supervised, each policy algorithm, and mixed plans by strategy. A 40-rank result should identify which configuration completed, how much real work it did, how the ranks agreed on updates, what happened after restart and what throughput it achieved. The historical claim remains attached to the historical commit until a current run supplies those measurements.
